### 1.2. Аналіз та опис знайдених портів

Серед отриманого результату виділимо відкриті мережеві порти різного призначення:

| Протокол (TCP / UDP) | Порт | Стан (State) | Локальна адреса | Служба / Призначення |
| :---: | :---: | :---: | :---: | :--- |
| **TCP** | **22** | `LISTEN` | `0.0.0.0:22` / `[::]:22` | **SSH (Secure Shell)** — служба безпечного віддаленого доступу та адміністрування системи. Прослуховує всі IPv4 та IPv6 інтерфейси. |
| **TCP** | **3306** | `LISTEN` | `0.0.0.0:3306` / `[::]:3306` | **MySQL / MariaDB** — сервер реляційної бази даних (прослуховується проксі-сервісом контейнеризації). |
| **TCP** | **5432** | `LISTEN` | `0.0.0.0:5432` / `[::]:5432` | **PostgreSQL** — сервер реляційної СУБД. |
| **TCP** | **6379** | `LISTEN` | `0.0.0.0:6379` / `[::]:6379` | **Redis** — in-memory сховище даних (кеш/брокер повідомлень). |
| **TCP** | **8000** | `LISTEN` | `0.0.0.0:8000` / `[::]:8000` | **HTTP-сервіс (Web alternative)** — вебзастосунок. |
| **UDP** | **53** | `UNCONN` | `127.0.0.53:53` / `127.0.0.54:53` | **DNS (Domain Name System)** — локальний сервіс кешування та резолвінгу доменних імен (`systemd-resolved`). |
| **UDP** | **68** | `UNCONN` | `192.168.8.34:68` | **DHCP Client** — клієнтський порт протоколу динамічної конфігурації мережі (BOOTPC / DHCP). |

#### Пояснення станів:
* **`LISTEN` (для TCP):** Сокет переведено в пасивний режим очікування вхідних з'єднань від клієнтів (готовий прийняти запит на встановлення сесії TCP 3-way handshake).
* **`UNCONN` (Unconnected, для UDP):** Оскільки протокол UDP є безсесійним (connectionless), поняття постійного з'єднання чи стану прослуховування для нього відсутнє. Сокет просто прив'язаний до локального порту і готовий приймати чи надсилати окремі дейтаграми.

### 2.2. Ідентифікація процесів та їхніх портів

З отриманого виводу зафіксуємо ключові системні процеси:

#### Процес 1: `sshd`
* **Назва процесу:** `sshd` (OpenSSH Daemon)
* **PID процесу:** `1262492` (також асоційований з systemd PID: `1` через сокет-активацію)
* **Протокол та порт:** **TCP 22** (`0.0.0.0:22`, `[::]:22`)
* **Опис:** Системний демон захищеного шелу для віддаленого входу та адміністрування.

#### Процес 2: `docker-proxy` (для PostgreSQL)
* **Назва процесу:** `docker-proxy`
* **PID процесу:** `290375` (IPv4) та `290381` (IPv6)
* **Протокол та порт:** **TCP 5432**
* **Опис:** Компонент Docker, який перенаправляє трафік з хостового порту `5432` у відповідний Docker-контейнер СУБД PostgreSQL.

#### Процес 3: `docker-proxy` (для Redis)
* **Назва процесу:** `docker-proxy`
* **PID процесу:** `290404` (IPv4) та `290412` (IPv6)
* **Протокол та порт:** **TCP 6379**
* **Опис:** Проксі-демон Docker для прокидання порту сервера Redis у контейнер.

#### Додатковий процес: `systemd-resolve`
* **Назва процесу:** `systemd-resolve`
* **PID процесу:** `1261674`
* **Протокол та порт:** **UDP 53** / **TCP 53** (`127.0.0.53:53`, `127.0.0.54:53`)
* **Опис:** Локальний системний DNS-сервер (stub resolver), який обслуговує резолвінг імен для ОС.

## Завдання 3. Перевірка TCP-з’єднання

### 3.1. Виконана команда та результат

```bash
support@maincopy:~$ nc -vz google.com 80
Connection to google.com (142.250.130.139) 80 port [tcp/http] succeeded!
```

---

### 3.2. Аналіз результату

* **Цільовий вузол:** `google.com` (резолвиться в IPv4-адресу `142.250.130.139`).
* **Тип з’єднання:** **TCP (Transmission Control Protocol)** — транспортний рівень L4.
* **Використаний порт:** **80** (стандартний порт протоколу прикладного рівня `http`).
* **Результат перевірки:** **З’єднання успішно встановлено (`succeeded!`)**.

#### Технічний механізм:
Утиліта `nc` (Netcat) із прапорцем `-z` (режим сканування/перевірки без надсилання корисних даних) ініціювала процедуру встановлення зв'язку **TCP Three-Way Handshake** (тристороннє рукостискання):
1. **SYN:** Клієнт надіслав пакет із прапорцем `SYN` на IP `142.250.130.139:80`.
2. **SYN-ACK:** Вебсервер Google прийняв запит і відповів пакетом `SYN-ACK`.
3. **ACK:** Клієнт підтвердив отримання пакетом `ACK`.

Оскільки рукостискання завершилось успішно, операційна система підтвердила готовність повнодуплексного з'єднання, про що Netcat повідомив у терміналі.

## Завдання 4. Порівняння TCP vs UDP

### 4.1. Виконані команди та результат

```bash
support@maincopy:~$ nc -u -vz 8.8.8.8 53
Connection to 8.8.8.8 53 port [udp/domain] succeeded!

support@maincopy:~$ nc -vz 8.8.8.8 53
Connection to 8.8.8.8 53 port [tcp/domain] succeeded!
```

---

### 4.2. Порівняння та фіксація різниці в поведінці TCP і UDP

Хоча в обох випадках `nc` повідомив про `succeeded!`, під капотом відбуваються принципово різні мережеві процеси:

| Критерій порівняння | TCP (`nc -vz 8.8.8.8 53`) | UDP (`nc -u -vz 8.8.8.8 53`) |
| :--- | :--- | :--- |
| **Тип з'єднання** | **Connection-oriented** (орієнтований на встановлення логічного з'єднання). | **Connectionless** (без встановлення з'єднання, дейтаграмний). |
| **Рукостискання (Handshake)** | **Присутнє:** обов'язкове тристороннє рукостискання (SYN $\rightarrow$ SYN-ACK $\rightarrow$ ACK). | **Відсутнє:** дані просто надсилаються у сокет без жодного попереднього погодження. |
| **Гарантія доставки та стан** | **Є 100% підтвердження:** `succeeded!` гарантовано означає, що віддалений сервер живий, порт відкритий і прийняв підключення. | **Немає гарантії:** `succeeded!` у Netcat лише означає, що локальна ОС успішно сформувала і відправила UDP-пакет у мережу, а у відповідь **не надійшло** ICMP-повідомлення «Port Unreachable». Сервер міг навіть проігнорувати пакет. |
| **Контроль цілісності та черговості** | Номери послідовності (Sequence/ACK numbers), контроль потоку (Flow Control), повторна передача втрачених сегментів (Retransmission). | Відсутній. Пакети можуть губитися, дублюватися або надходити не за порядком. |
| **Накладні витрати (Overhead)** | Більший розмір заголовка (мінімум 20 байт), більші затримки (latency) через необхідність підтверджень. | Мінімальний заголовок (8 байт), максимальна швидкість і мінімальна затримка. |

#### Чому DNS (порт 53) підтримує обидва протоколи?
* **UDP 53:** Використовується для переважної більшості стандартних клієнтських DNS-запитів, оскільки запит і відповідь зазвичай малі (до 512 байтів) і потребують мінімальної затримки.
* **TCP 53:** Використовується для передачі зон між DNS-серверами (Zone Transfers: AXFR/IXFR), або коли розмір DNS-відповіді перевищує ліміт UDP (наприклад, складні відповіді з DNSSEC) і встановлюється біт TC (Truncated).

### 5.1. Виконана команда та результат


---

### 5.2. Аналіз параметрів DNS-відповіді

1. **Досліджуваний домен:** `neoversity.com.ua`
2. **Отримані IP-адреси домену (A-записи):**
   * **`3.248.56.152`**
   * **`18.202.8.75`**
   * **`54.155.19.65`**
   *(Наявність одразу кількох IP-адрес свідчить про балансування навантаження Round-Robin DNS та відмовостійкість інфраструктури в хмарі AWS).*
3. **DNS-сервер, який надав відповідь:**
   * **IP-адреса DNS-сервера:** `127.0.0.53` (порт `53`).
   * **Що це за сервер:** Це локальний кешуючий заглушковий резолвер (**systemd-resolved stub resolver**), який працює безпосередньо всередині Linux. Він перехоплює локальні DNS-запити від програм, перевіряє свій локальний кеш, а у разі промаху кешу запитує зовнішні DNS-сервери (отримані по DHCP або налаштовані статично) та повертає результат клієнту.
4. **Статус «Non-authoritative answer» (Неавторитетна відповідь):**
   * Означає, що DNS-відповідь була отримана не від первинного (авторитетного) сервера імен, де безпосередньо зберігається зона домену `neoversity.com.ua`, а з кешу проміжного рекурсивного резолвера.
